# Architecture Decision Records

## ADR-001：双采集 API

- 状态：Proposed，待 Board 批准
- 决策：麦克风采用 AVFoundation；系统音频采用 ScreenCaptureKit。SCK 配置只消费音频，不持久化屏幕帧，并排除本应用音频。
- 理由：均为 Apple 原生、与 macOS 权限模型一致；职责分离清晰，能分别报告输入失败。
- 备选：Core Audio aggregate device（配置复杂、依赖系统设备拓扑）；仅 SCK 捕获所有音频（麦克风控制与权限语义较弱）；虚拟音频驱动（安装与发布成本超范围）。
- 取舍：两套回调和时钟需协调；接受该复杂度，分轨并记录时间元数据。
- 后果：最低 macOS 暂定 13；部署目标变化需重新审批。

## ADR-002：分轨而非实时合流

- 状态：Proposed
- 决策：每会话生成 microphone/system 两个独立工件，共享会话时间基准；不实时混音。任一路不可用即启动失败。
- 理由：保留证据、隔离故障、避免在尖刺中引入重采样/增益/漂移掩盖；未来转写可独立处理。
- 备选：实时混为单文件（用户播放简单，但失败难诊断且不可逆）；同时保存分轨和混音（重复存储和实现范围扩大）；单路降级（违反“双路同时采集”验收语义）。
- 取舍：用户需分别试听两轨；第一里程碑以验证性优先。

## ADR-003：CAF + 32-bit Float LPCM

- 状态：Proposed
- 决策：各轨按来源实际采样率/声道数保存 32-bit Float LPCM CAF，不在采集路径重采样。
- 理由：与 Apple 音频 buffer 贴近、编码失败面小、便于检查 frame；CAF 对未知/较长时长更稳健。
- 备选：WAV PCM（兼容广但容器大小限制/头提交考虑）；M4A/AAC（文件小但编码器引入失败、损耗和延迟）；统一 48kHz（便于对齐但需实时转换）。
- 取舍：文件较大；尖刺录制时长和本地空间预检控制风险。后续产品格式另立 ADR。

## ADR-004：应用容器内本地持久化与隐私

- 状态：Proposed
- 决策：写入 Application Support 的应用私有相对目录；`.partial` → 校验 → 原子改名；无上传、无远端遥测；日志白名单化。
- 理由：最小权限、本地优先、失败工件不冒充成功，符合 AI-1 v2 隐私边界。
- 备选：用户每次选择目录（增加授权/失败分支）；Documents（暴露面更大）；云存储（明确超范围且有持续成本/隐私风险）；自动删除（可能破坏验收证据）。
- 取舍：用户发现文件需“显示位置”；正式保留/删除策略留后续规格。

## ADR-005：显式状态机与原子化会话

- 状态：Proposed
- 决策：协调器作为唯一状态所有者，串行处理事件；只有两路首 buffer 后进入 recording，只有两份 final 工件后进入 succeeded。
- 理由：防止 UI、异步权限与双回调竞态；状态含义可测试、可审计。
- 备选：由 SwiftUI view 拼接布尔值（非法组合多）；每组件自行发布状态（冲突与错误覆盖）；单路先录再补另一条（会产生不可解释片段）。
- 取舍：需要明确事件和超时注入；提升可验证性。

## ADR-006：分层测试策略

- 状态：Proposed
- 决策：纯状态机/契约/文件生命周期用确定性单元测试和 failure injection；组件集成用受控 fake buffers/临时容器；真实权限、SCK 系统音频与播放使用实体 macOS 手工验收并保存脱敏证据。QA 与 Code Review 的独立门仅在另行获批创建后执行。
- 理由：系统权限和真实音频不可在普通 unit test 中可靠自动化；纯逻辑仍应高速覆盖。
- 备选：只做端到端手测（回归慢且错误分支难触发）；全自动 UI 权限测试（系统弹窗脆弱、需特权）；依赖真实用户录音（隐私禁止）。
- 取舍：尖刺最终“已验证”需要人工环境；在独立 QA Agent 未获批前只能标记实现者验证，不能宣称独立验证完成。

## ADR-007：播放失败不改变录音成功

- 状态：Proposed
- 决策：录音会话成功与播放尝试是正交结果。有效双工件存在时会话保持 succeeded；播放失败通过 playback 事件/错误呈现。
- 理由：播放设备/解码失败不应错误否定已落盘的录音证据。
- 备选：播放失败令 session failed（语义混淆且妨碍重试）；自动删除不可播文件（破坏诊断证据）。
- 取舍：UI 同时呈现“录音已保存”和“播放失败”，文案须清晰。
